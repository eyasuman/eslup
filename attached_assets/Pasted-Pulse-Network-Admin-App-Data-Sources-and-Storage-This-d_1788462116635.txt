Pulse Network Admin App: Data Sources and Storage
This document explains what the Pulse Network admin app displays, how it collects the data, where each dataset is stored, and which Supabase Storage buckets are used for files.

1. High-level data flow
The admin app has three layers:

Expo / React Native admin app
        |
        | HTTPS JSON requests under /api
        v
Pulse API server (Express)
        |
        | Supabase REST API and Supabase Storage API
        v
PULSE Supabase project

The mobile app uses artifacts/mobile/context/DataContext.tsx as its data gateway. When the app starts, DataProvider.refresh() requests these resources in parallel:

GET /api/providers
GET /api/appointments
GET /api/revenue
GET /api/institutes
GET /api/banners
GET /api/reviews
GET /api/patients
GET /api/audit
GET /api/teleradiology
GET /api/settings

The API server is mounted under /api in artifacts/api-server/src/app.ts. Its Supabase connection is implemented in artifacts/api-server/src/lib/supabase.ts.

The Supabase project URL is configured in the API server.
SUPABASE_SERVICE_KEY is used only by the API server.
The service key must never be bundled into the Expo application.
Production Android/iOS builds use the API URL configured in artifacts/mobile/eas.json.
In the web preview, the mobile app calculates the API host from the current preview host.
The API normalizes both camelCase and snake_case column names where needed, so the mobile app receives one consistent response shape.

3. Detailed dataset descriptions
3.1 Providers and doctor licenses
Database source: doctors

The provider list reads all doctor/provider records and sorts them by newest creation date. Provider data shown by the app includes:

id, userId, name, providerType, specialty
status, email, phone, city
consultationFee, experienceYears
licenseNo, licenseFile
avatarUrl, bio, service modes, and creation date
Valid provider statuses are:

Active | Pending | Disabled | Declined

The License Review screen selects records where:

doctors.status = "Pending"
AND doctors.licenseFile IS NOT NULL

How the license file is located
The API does not expose the private license as a public URL.

It loads the provider from doctors.
It reads an upload ID from one of:
doctors.licenseFile.uploadId
doctors.licenseUploadId
doctors.license_upload_id
If an upload ID exists, it looks up the active row in user_uploads.
It takes bucket, storage_path, and original_name from that metadata row.
If no upload metadata resolves the path, it falls back to:
bucket: medical-licenses
path: licenseFile.path
It creates a short-lived signed URL. The current expiration is 600 seconds (10 minutes).
The active upload metadata query is equivalent to:

user_uploads
  where id = <upload id>
  and status = "active"
  select bucket, storage_path, original_name

License buckets
Bucket	Visibility	Purpose
user-uploads	Private in the normal upload-metadata flow	Current uploaded user/license files; the exact bucket is read from user_uploads.bucket
medical-licenses	Private	Legacy/default license bucket when no resolved upload metadata is available
The API returns a signed URL only for the individual review request. The mobile app should not construct a public license URL.

Approving a license changes doctors.status to Active; rejecting it changes the status to Declined. Both actions also create an audit entry.

3.2 Appointments and payment proofs
Database source: appointments

The appointment list reads all appointment records, newest first. The admin app uses fields such as:

doctor and patient names
appointment status and date
service type
consultation fee, platform fee, and total price
payment status
payment proof URL
transaction ID
sender name
payment method
Payment Review focuses on records where:

appointments.paymentStatus = "pending"

If an appointment has a payment proof URL but no payment status, the API normalizes its status to pending.

Payment proof bucket
When paymentProofUrl is stored as a relative path rather than a complete HTTP URL, the API turns it into a public Supabase URL in the:

payment-proofs

bucket.

If the database already stores a complete HTTP URL, the API passes that URL through unchanged. The admin action updates appointments.paymentStatus to one of:

pending | verified | rejected

When a scheduled appointment is marked verified, the patient consultation can be unlocked by the patient app's Supabase Realtime subscription to that appointment row.

3.3 Revenue
There are two related revenue sources:

Monthly revenue screen: GET /revenue reads the revenue table, ordered by month.

Dashboard platform revenue card: calculated in the mobile app from completed appointments:

sum(appointments.platformFee where appointments.status = "completed")

The revenue screen also calculates some values from appointments, including completed platform fees and the average consultation fee.

Revenue fallback behavior
If the revenue table is empty or the request fails, the API currently returns generated six-month stub data. That fallback is intended to keep the dashboard rendering, but it is not a source of financial truth. Production reporting should ensure the revenue table is populated and should treat generated fallback values as non-authoritative.

3.4 Institutes
Database source: institute_pulse

The Institutes screen reads institute records and can create a new record or change its status. Stored fields include:

name, type, status, city, and address
phone, email, and license number
doctor count and bed count
services and accreditations
Valid institute statuses are:

Active | Pending | Suspended

No institute storage bucket is used by the admin API.

3.5 Promotional banners
Database source: banners

The banner record stores:

title and message
type
active/inactive state
priority
promo code
image URL, video URL, and link URL
display duration
creation date
Banners are read in descending priority order. The admin can create, activate or deactivate, and delete banner records.

Banner image bucket
Uploaded images are sent to POST /banners/upload-image as base64 data. The API:

Accepts PNG, JPEG, WebP, or GIF.

Rejects files larger than 5 MB.

Creates a path in the form:

banners/<uuid>.<extension>

Uploads the object to the public:

banners

bucket.

Returns the public URL.

The returned URL is then stored in banners.imageUrl when the banner is created.

The banners bucket is the only bucket written by the banner upload endpoint. Video URLs are stored as URL values; the admin API does not upload video objects.

3.6 Reviews
Database source: reviews

The review screen reads:

doctor and patient identifiers/names
rating and comment
moderation status
creation date
Valid review statuses are:

visible | pinned | banned | shadow_banned

Changing a review status updates the reviews row and writes an audit record. No review storage bucket is used.

3.7 Patients
Source: derived from appointments

There is no standalone patients table used by this admin API. The patient list is built by selecting these appointment fields:

patientId, patientName, patientEmail, createdAt

The API groups rows by this key, in priority order:

patientId
patientEmail
patientName
For each group it calculates:

patient ID
name and email
total appointment count
first-seen creation date
a display status of active
Phone and city are not available from this query and are returned as null. The patient screen is intentionally read-only. The PATCH /patients/:id/toggle endpoint returns HTTP 409 because a patient account status cannot be persisted without a patient table or another authoritative account source.

No patient storage bucket is used.

3.8 Audit log
Database source: auditLogs

The audit screen reads audit records newest first. Each record contains:

actor name
action text
object type
type: Admin, User, or System
timestamp
The API writes audit records for admin mutations including provider changes, license decisions, payment decisions, institute changes, banner changes, review changes, teleradiology changes, and settings changes.

Audit writes are isolated from the primary mutation. If an audit insert fails, the main operation is not rolled back; the error is logged by the API server.

No audit storage bucket is used.

3.9 Teleradiology
Database source: teleradiologyCases

The admin screen reads and updates case status. Displayed fields include:

case ID
patient and radiologist names
imaging modality and body part
status, priority, and notes
creation date
Valid case statuses are:

pending | in-review | completed | urgent

No teleradiology storage bucket is referenced by the current admin API. If future imaging files are added, they should be documented separately rather than assumed to use one of the existing buckets.

3.10 Platform settings and admin gateway
Database source: settings

The settings screen reads and updates:

fixed platform fee
cancellation notice period
cancellation penalty
reminder cadence
gateway password
inactivity timeout
The API maps the mobile names to database columns:

Mobile/API name	Stored column
platformFee	fixedPlatformFee
cancellationNoticePeriodHours	noticePeriodHours
cancellationPenaltyFee	penaltyFee
reminderCadence	reminderCadence
gatewayPassword	gatewayPassword
inactivityTimeoutMinutes	inactivityTimeoutMinutes
The gateway lock is enforced by the Expo app. On startup, the app loads the settings record, compares the entered PIN/password with settings.gatewayPassword, and locks again after the configured inactivity period or when the app leaves the active state.

Feature toggles such as Maintenance Mode, New Registrations, and Reviews are currently local UI state only. They are not included in the API settings payload or persisted in the settings table.

No settings storage bucket is used.

Bucket	Used by	File type	Access behavior

6. Important implementation notes
Optional resource fallback
DataContext uses a safe fetch wrapper for initial loading. If an optional endpoint fails, the corresponding resource becomes an empty array, while settings use defaults. This prevents one unavailable dataset from blocking the whole admin console, but an empty screen can also indicate an API or Supabase problem.

Data is not cached permanently in the mobile app
The data context holds the current session's data in React state. Pull-to-refresh calls the same API endpoints again. Database persistence happens in Supabase through the API server.

API security boundary
The Supabase service key is server-only. The mobile app sends ordinary JSON requests to the API and never receives the service key. The admin gateway provides the app's UI lock, but it should not be treated as a replacement for server-side authentication and authorization if the API is exposed publicly.
